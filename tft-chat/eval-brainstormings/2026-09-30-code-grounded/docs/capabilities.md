# ChatTFT evidence contract inspected September 30, 2026

This is a translation of research requirements into the current public tool boundary. It does not certify that a populated Set 18 evaluation database exists. Source files, the original collection and application configuration are unchanged. Paths below are relative to the repository root.

## Evidence sources and scope

`app/backend/src/domain/tools/__init__.py` registers the tools. `db_tools/models.py`, `cohort_tools.py`, `ranking_tools.py`, `deltas.py`, `cohort_query.py` and `utils.py` under that directory are authoritative for their schemas and behavior. The analyst can access ranking, cohort, delta and context tools; chat reaches cohort tools through `data_analyst`. `final_responder` synthesizes results. Composition workbench APIs are not registered assistant tools.

Every database call reads the selected database's active, ready analysis scope. That scope selects patch, queue and set; there are no per-call patch, timestamp, rank or scope-ID arguments. `evals/utils.py:evaluation_database` supports a database name in case metadata, then suite metadata, then the configured evaluation target. A database name does not freeze its contents or change repository context's configured set. Do not invent a database name in an import file. The prepared datasets inherit the evaluation target until an operator pins a verified database at execution time.

Before a scored statistical run, the operator must verify a Set 18 standard-ranked scope, ready facts, a stable dataset revision, the actual collection interval and available population provenance. Region/platform are groupable diagnostics; player rank and timestamps are not exposed by these tools. Patch extraction normalizes versions and does not itself prove a B-patch/hotfix time cutoff. Questions explicitly about 18.3B need a compatible supplied scope manifest; current configuration must not be silently treated as such a manifest. Pre/post analysis needs separate data snapshots/runs and an externally supplied comparison record. Case metadata describing these requirements is descriptive, not a runner-enforced filter.

The context corpus is `app/backend/src/resources/context/set18/`: `unit_context.md`/`.json`, `items/catalogue.*`, `items/special.*`, `traits/major.*`, `traits/horizontal.*`, and the detailed trait tables. Use it for identities, item families and candidate trait thresholds, not performance. The baseline labels itself 18.1; September 20 supplements target 18.2 (`docs/content_providers/set18-context.md`). It is not a verified 18.3B rules snapshot. A retrieved file or `complete_selected_collections: true` establishes retrieval completeness, not patch correctness. Resolve query identities with `resolve_tft_names`; use `request_additional_context` if initial context is insufficient. Do not require that context call when the facts were already injected.

## Supported operations

| Research wording | Current operation | Metrics and constraints |
| --- | --- | --- |
| Find actual item builds | `rank_unit_loadouts` | Exact unit/star/item count; up to two required item terms bind distinct slots, including repeated terms. Returns `item_1..3`, canonical loadout, `boards`, `unit_boards`, `loadout_pick_rate`, mean/top4/win. A trait condition means active at any tier. No arbitrary cohort argument. |
| Compare finished allocations or packages | `compare_cohorts` | Shared context plus explicit target/baseline, or target versus complement. Returns cohort `boards`, `histogram`, mean/top4/win, target-minus-baseline `effects`, overlap and warnings. |
| Discover support and check composition of a population | `query_cohort` | One to three dimensions per call; `distinct_boards`, `distinct_lobbies`, `pick_rate`, mean/top4/win; page with `has_more`. Dimensions include unit/name/star/loadout/item count, item/name/slot, trait/name/medal/contribution count, placement, level, board_size, completed_item_count, region/platform. |
| Find recurring partners and contextual associations | `get_cohort_unit_deltas`, `get_cohort_item_deltas`, `get_cohort_trait_deltas` | Frequency ordered, not best-outcome ordered; exact-star/holder/medal breakdowns available. `delta` compares presence versus absence inside the cohort; `relative_delta` compares the same entity inside versus outside the cohort. Negative placement deltas are better. |
| Establish broad eligible entities or item families | `rank_units`, `rank_items`, `rank_traits` | Discovery marginals, not substitutes for joint allocation/package evidence. `rank_items.item_type` classifies a ranking; it is not a cohort-wide item-family filter. |

`FilterGroup` is conjunctive. Unit predicates support exact star, copy bounds and completed-item-count bounds. Item predicates support exact name, holder, holder star and multiplicity. Trait predicates support active state, named medal, style, total-tier count and contributing-unit bounds. Final level is exact or ranged. Explicit absence of a named unit/item uses minimum and maximum copies zero; omitted minimum defaults to one and would contradict maximum zero. No nested OR/NOT list or arbitrary SQL is available.

Important implementation details:

1. Separate holder-bound item predicates count matching items across all copies of that named holder. To certify that a full trio is on one unit, require exactly one copy of that holder across all stars, then separately constrain its star and completed-item count. Restricting only the count of two-star copies is insufficient if another one-star copy can carry a requested item. `rank_unit_loadouts` already binds its items to one occurrence.
2. Cohort membership filters select boards. They do not restrict rows joined for grouping. A query requiring Ahri and grouped by `unit_name` returns all unit identities on qualifying boards, not only Ahri. Include the entity name dimension and select the relevant returned row before interpreting its loadout, stars or traits. Multiple same-board trait rows do not give a joint two-trait vector; require both named trait conditions in the cohort for the intersection.
3. `tier` is a medal string, not a numeric breakpoint. For questions about three/four/six contributing units, use contribution bounds and verify activation against patch-compatible rules. A threshold such as six may cover six or seven contributors until the next breakpoint; exact six contributors is a stricter, explicitly named slice. `total_tier` is not the current active breakpoint.
4. `active: false` requires an existing inactive trait record; it does not match a missing trait row. For genuinely without-active-trait comparisons, use the complement of the active target within a shared family. Missing/malformed data are still a scope-quality issue, not proof of absent mechanics.
5. `board_size` is the number of stored unit records (`AnalysisBoard.unit_count`), not player level, occupied capacity, or an exact roster signature. Elder Dragon and capacity modifiers make those concepts diverge. Named roster conditions alone establish contains-all membership. If N distinct identities are all required, a reportable query_cohort group with board_size=N establishes that those N identities exhaust the stored unit records for that group. Use that row’s own outcomes and denominator. This does not certify occupied capacity or game legality, and compare_cohorts cannot inherit that grouped-row restriction.
6. Public rows and nonempty comparison cohorts require at least 50 boards. Empty comparison cohorts can explicitly report zero; a missing ranking row or suppressed group cannot be called zero. Compare intervals require at least 50 boards in each cohort and 30 lobbies in the selected population. Per-placement grouped query rows also face the 50-board floor, whereas a reportable comparison summary returns its histogram. Do not reconstruct hidden groups from totals.
7. Rates are fractions; average placement is lower-is-better. `games` and `boards` are board samples, `holds` counts item instances. Comparisons return target-minus-baseline estimates; placement and rate improvements have opposite signs. SDK output rounds numerical values to at most two decimals. Do not assert exact raw floating-point equality or derive precise counts by multiplying rounded rates. Histogram-derived counts are preferable where exposed.

## Requirements that need translation or additional preparation

`board_size`, total `completed_item_count`, region and platform can be grouped, but cannot be filtered in `FilterGroup`. Use reportable grouped slices for descriptive like-for-like comparisons; do not claim `compare_cohorts` held those dimensions fixed. There are no filters for global number of artifacts/radiants/emblems, upgraded-board cost, all-three-star count, generic AP/AD/defensive item categories, main-tank role, arbitrary unit pair axes or a complete-roster signature filter. Fully enumerated rosters can still use the grouped-row closure proof above; unknown or partial cores cannot. Named items/units can define a bounded proxy; exhaustive family exclusions can exceed the 24-condition/64-predicate bounds. Inspect global inventories descriptively and state the remaining confounder. Whole-board exclusion or exact-budget claims remain preparation/capability gaps unless actually certified.

For discovery, repeat bounded cohort queries with candidate anchors and then verify conjunctions. Marginal partner frequencies do not establish a recurring joint core. A shortlist is explicitly limited to inspected candidates/pages, not an exhaustive clustering of all boards. The private composition workbench is not a shortcut around this restriction.

Final-board data cannot identify attempted rerolls, investment timing, win probability after choosing a comp, fight duration, damage share, item effects as causes, Alpha Mark ownership, Blackthorn sacrifice, Eternal Pact partner, accumulated stacks, or Adaptor form from an item label. Lux identity must be resolved to an observable variant; generic Lux plus a board trait does not prove its chosen origin. Keep unsupported claims out of gold answers.

## Scoring without inventing answers

The deliverable is an evidence-relative investigation benchmark: expect the assistant to investigate and report the result actually returned, not a preselected winner. Each case has specific cohort definitions, metrics and failure conditions. `expected_output.requirements` feeds the existing `answer_quality` judge. However, `evals/utils.py:execution_evidence` sends a bounded trace summary and presentation-event extract, not full analytical tool outputs. Full outputs remain in trace observations. Therefore the default judge can assess the answer's coverage and visible reasoning, but cannot independently certify every quoted number or nested cohort argument against raw tool results. This is a material grading limitation, not a solved verification step. For numerical gold scoring, capture a compatible immutable aggregate reference into expected output or separately audit full trace outputs; neither has been fabricated here.

Native trace checks cover named tool invocation, partial argument containment, selected top-level resolved-name flow, handoff/final-agent or response regex. There is no native arbitrary tool-output predicate, nested resolved-name path, general arithmetic checker or ordered call-sequence DSL. Complex validity and interpretation live in requirements; they are not falsely labeled deterministic. The prepared items benchmark investigation behavior and answer coverage now; promotion to validated factual gold additionally needs the scoped observations and an adequate evidence-to-grader route.

An importable dataset is not a measured gold dataset. Missing scope, missing identities or suppressed outcomes must be reported as data/preflight limitations, not counted as proof the underlying gameplay question is answered. The actual outcome benchmark should be run only with sufficient applicable data. No generic abstention response satisfies a supported case.
